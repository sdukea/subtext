# Implementation Decisions

Product and strategy decisions are in `research/DECISION_LOG.md`. This file records the engineering decisions made while building.

| # | Date | Decision | Rationale | Alternatives |
|---|---|---|---|---|
| D-1 | 2026-11-18 | Build now, even though research `00`/`14` recommends a 4-week validation sprint before production code | The founder chose to move to implementation. The build doubles as the Wizard-of-Oz prototype and benchmark harness that Phase 0 needs. Kill criteria in `01` §4 still apply | Wait for interviews and fake-door tests |
| D-2 | 2026-11-18 | Scope = the research's *narrowed* product (pre-flight brief builder with app-builder and coding-agent renderers), while the general-assistant path still works | Resolves a conflict: the user brief describes a general tool, research recommends the builder niche. One engine covers both, and the target selector carries the niche | General-only; builder-only |
| D-3 | 2026-11-18 | Stateless server: the client holds `ConversationState` and sends it with each action; Zod validates it in both directions; history lives in `localStorage` | No accounts or memory in this slice, so Postgres would add infrastructure with no requirement behind it (user brief §4). The state is replayable and testable. Tampering only affects the user's own session | Postgres JSONB now (research `08` §7) — to adopt with accounts/memory (F9) |
| D-4 | 2026-11-18 | Stage A merges analysis and question proposal; question *selection* stays in code | The latency experiment suggested in `08` §4.2. Saves a round trip, and code keeps the ask/stop decision, which LLMs are measurably bad at (`06` §0.3) | Separate propose stage |
| D-5 | 2026-11-18 | Uncertainty = K parallel samples choosing among candidates enumerated by Stage A, with Dirichlet smoothing | Turns sampling into a classification task, so clustering is trivial and the candidates double as answer options. The API no longer accepts `temperature`; per-sample option rotation adds diversity and offsets position bias | Free-text samples + embedding clustering; verbalised confidence (rejected by `06` §D.4) |
| D-6 | 2026-11-18 | Models: Haiku 5.5 (analysis/sampling, thinking off, effort low); Sonnet 5.5 (compose, adaptive thinking, effort low, `fallbacks: "default"`) | Research `08` §8.1 "Config B": question turns must be fast, composition must be good. Configurable via env | Single model for all stages |
| D-7 | 2026-11-18 | Renderers vary *structure* by target × family but use plain Markdown for every vendor | Whether vendor-specific syntax helps is unproven (OQ-8). Structural adaptation addresses the brief's "no rigid template" requirement | XML for Claude, Markdown for GPT |
| D-8 | 2026-11-18 | Deterministic fallback composer, also used by the mock | The user always gets a prompt (`08` §8.2). It never pretends to be AI output: the source label and banner say what it is | Hard error on compose failure |
| D-9 | 2026-11-18 | `repairIR` restores user-confirmed facts the composer dropped and warns the user | Intent preservation (`04` §7: about 26% of rewrites lose intent). Cheap and deterministic | LLM critique pass (extra latency) |
| D-10 | 2026-11-18 | No deep links to ChatGPT/Claude; Copy is primary | Research D5 / `07` §0.8: undocumented, truncated and injection-prone | `?q=` links |
| D-11 | 2026-11-18 | Typography: IBM Plex Sans/Mono; one accent (deep teal); hairline rules; light and dark | Research `07` §12 visual direction; avoids the generic "AI slop" look (`04` §8.13) | Inter/system UI |
| D-12 | 2026-11-18 | The eval judge defaults to Opus 5.5 (same provider family as the generator) | Only Anthropic credentials are assumed. The bias is documented in every report; adding a cross-provider judge is a tracked TODO | GPT/Gemini judge |
| D-13 | 2026-11-20 | Treat this build as the Phase 0 validation prototype. Add only what helps test the thesis: Wizard-of-Oz study mode, the 60-task benchmark with T3L/T5/oracle arms, and length-controlled stats | Founder's brief: respect the 4-week evidence sprint and build the smallest credible prototype; research/14 Phase 0 | Production MVP features (accounts, Postgres, streaming) |
| D-14 | 2026-11-20 | Wizard-of-Oz runs inside the real product: the engine still analyses and proposes, its round is withheld as `proposals`, and an operator publishes the round. Every question records its source (`model` / `operator_selected` / `operator_edited` / `operator_written`) | The participant experience must be identical across conditions, and operator questions must never be passed off as the model's (founder's brief §7). Keeping the engine's proposals shows exactly where humans disagree with the policy | A separate WoZ mock-up; a human typing into a chat |
| D-15 | 2026-11-20 | Study sessions: the server-side state (JSON files in `.data/studies`, git-ignored, atomic writes, per-study lock) is authoritative. Normal sessions stay stateless and browser-held | The operator and participant use different browsers. A one-machine research prototype doesn't justify a database (D-3 still holds for normal use) | Postgres now; in-memory only (lost on restart) |
| D-16 | 2026-11-20 | Operator endpoints need `SUBTEXT_OPERATOR_KEY` if it's set; without it they work only outside production | Protects participant data without building accounts | Full auth |
| D-17 | 2026-11-20 | Convergence stop: after ≥ 1 round, stop when the impact-weighted agreement of sampled interpretations is ≥ 0.8 on every remaining choice question (no free-text or contradiction questions pending) | research/06 §F.6 in a simplified form that uses the samples already taken; no extra calls. The full output-divergence test is deferred until outcome data can calibrate it | Compile M candidate prompts and compare downstream sketches (≈ 3–6 extra calls per check) |
| D-18 | 2026-11-20 | One contradiction question per round, surfaced as a single confirmation; answered contradictions become explicit must-have decisions in the spec | research/06 §H.4. Verification found that contradiction answers were silently dropped | Several contradiction cards at once |
| D-19 | 2026-11-20 | Saved context ("Remember this") lives in browser localStorage, fills a slot only when the current request leaves it open (precedence: edit > answer > stated > remembered > default), and is ignored in study sessions | research/13 F9 without accounts. Equal starting information across study conditions | Server-side memory with accounts |
| D-20 | 2026-11-20 | Renderers vary by target first: app builder = numbered build order, "not in this version", working rules on scope and reporting; coding agent = constraints before requirements, verification, repository rules; generic = deliverable-first, no working rules | The founder's brief requires the target to change the spec materially, not just its headings | Family-driven headings only (previous behaviour) |
| D-21 | 2026-11-20 | Benchmark items live in `eval/data/benchmark-v0.json`, validated with Zod at load time. All 60 were authored with an AI assistant from research/09's schema, then reviewed by spot checks | A data file, not code, so researchers can edit it. Authored items aren't real user tasks, and the reports say so | Keep items in TypeScript |
| D-22 | 2026-11-20 | User-facing copy calls the output a "spec" ("Copy spec", "Your spec is ready") | The research repositions the product from prompt generator to brief/spec builder; the three central objects are Request, Brief, Specification | Keep "prompt" |
